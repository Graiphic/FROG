<section id="1-overview">
  <h2>1. Overview</h2>

  <p>Source provenance is the optional source-carried record of how selected <code>.frog</code> source objects were authored, generated, imported, modified, reviewed, or accepted.</p>

  <p>A FROG program may be edited graphically by a human, generated by an AI system, transformed by an automated tool, imported from another artifact, inserted from a snippet, or produced through a combination of these workflows. In the AI era, those paths SHOULD remain distinguishable when credible evidence is available.</p>

  <p>The purpose of source provenance is to allow tools to distinguish, without changing executable meaning:</p>

  <ul>
    <li>graph objects created through direct human authoring;</li>
    <li>graph objects generated or modified by AI assistance;</li>
    <li>graph objects produced by deterministic tooling;</li>
    <li>graph objects imported from external or unknown sources;</li>
    <li>graph objects explicitly reviewed and accepted by a human;</li>
    <li>graph objects whose previous attestation is stale, invalid, unsupported, or untrusted.</li>
  </ul>

  <p>Source provenance is not executable program meaning. It is authoring and audit metadata carried by source. A conforming runtime, compiler, backend, or lowering consumer MUST NOT use provenance to define what the program computes.</p>

  <pre><code>One-line model

canonical source object
        +
optional signed provenance attestation
        =
inspectable authoring evidence

not:

provenance
        -&gt; executable meaning</code></pre>
</section>

<hr />

<section id="2-why-source-provenance-exists">
  <h2>2. Why Source Provenance Exists</h2>

  <p>FROG is designed to be both machine-generable and human-inspectable. That dual nature is powerful, but it creates a new accountability problem: a valid <code>.frog</code> file may contain a mixture of direct human authoring, AI-generated source, deterministic tool output, and reviewed or unreviewed imported fragments.</p>

  <p>Without a provenance layer, an IDE can validate source shape and program meaning, but it cannot reliably tell the user which parts are known direct-human authoring, which parts came from a generator, which parts were later accepted by a human, and which parts are merely unknown.</p>

  <p>Source provenance exists so that a <code>.frog</code> file can carry inspectable authoring evidence without turning that evidence into language law.</p>

  <p>It supports questions such as:</p>

  <ul>
    <li>Was this node inserted through a trusted graphical authoring action?</li>
    <li>Was this edge generated by an AI assistant?</li>
    <li>Was this widget, region, or structure imported from a snippet?</li>
    <li>Has this AI-generated region been accepted by a human reviewer?</li>
    <li>Has the object changed since its last attestation?</li>
    <li>Is the attestation signed by an issuer trusted by the current organization, IDE, or workflow?</li>
  </ul>
</section>

<hr />

<section id="3-architectural-position">
  <h2>3. Architectural Position</h2>

  <p>Source provenance belongs to <code>Expression/</code> because it is serialized with canonical source and refers to source-visible objects.</p>

  <p>Its standardized home is the optional <code>ide.provenance</code> object. This keeps the provenance layer near authoring metadata while preserving the existing top-level source-section boundary.</p>

  <pre><code>.frog canonical source
  -&gt; optional ide.provenance evidence
  -&gt; structural validity
  -&gt; validated program meaning
  -&gt; FIR
  -&gt; lowering
  -&gt; backend contract
  -&gt; runtime / compiler / hardware bridge</code></pre>

  <p>The following distinctions MUST remain explicit:</p>

  <table>
    <thead>
      <tr>
        <th>Layer</th>
        <th>Role</th>
        <th>Provenance relationship</th>
      </tr>
    </thead>
    <tbody>
      <tr>
        <td><code>diagram</code></td>
        <td>Authoritative executable graph source.</td>
        <td>May contain source objects referenced by provenance subjects.</td>
      </tr>
      <tr>
        <td><code>front_panel</code></td>
        <td>Optional user-facing interaction composition.</td>
        <td>May contain widgets or bindings referenced by provenance subjects.</td>
      </tr>
      <tr>
        <td><code>ide.provenance</code></td>
        <td>Optional source-carried authoring evidence.</td>
        <td>May attest source object states but MUST NOT define execution semantics.</td>
      </tr>
      <tr>
        <td>Validated meaning</td>
        <td>Semantic interpretation of a structurally valid program.</td>
        <td>Does not depend on provenance for what the program computes.</td>
      </tr>
      <tr>
        <td>FIR</td>
        <td>Execution-facing representation derived from validated meaning.</td>
        <td>May preserve source mapping to provenance-covered objects but does not inherit provenance as semantics.</td>
      </tr>
    </tbody>
  </table>
</section>

<hr />

<section id="4-location-in-a-frog-file">
  <h2>4. Location in a <code>.frog</code> File</h2>

  <p>The provenance object, when present, is located at:</p>

  <pre><code>ide.provenance</code></pre>

  <p>Example top-level placement:</p>

  <pre><code>{
  "spec_version": "0.1",
  "metadata": { },
  "interface": { },
  "diagram": { },
  "front_panel": { },
  "ide": {
    "provenance": {
      "schema": "frog.source.provenance/0.1",
      "attestations": [ ]
    }
  }
}</code></pre>

  <p>If <code>ide</code> is omitted, provenance is absent. If <code>ide</code> exists but <code>ide.provenance</code> is omitted, provenance is absent. Absence MUST be interpreted as <strong>unknown</strong> or <strong>unattested</strong>, not as automatically AI-generated.</p>
</section>

<hr />

<section id="5-core-principles">
  <h2>5. Core Principles</h2>

  <ul>
    <li><strong>Optional source evidence</strong> — provenance MAY be carried in source, but a base <code>.frog</code> file does not require it.</li>
    <li><strong>Non-executable</strong> — provenance MUST NOT define, modify, or override executable meaning.</li>
    <li><strong>Fine-grain capable</strong> — provenance MAY target nodes, edges, structures, widgets, ports, bindings, annotations, changesets, or whole-document review bundles.</li>
    <li><strong>Digest-bound</strong> — an attestation SHOULD bind a claim to a digest of the covered source object state.</li>
    <li><strong>Signature-capable</strong> — an attestation MAY carry a cryptographic signature proving that an issuer made the claim over the covered state.</li>
    <li><strong>Trust-policy interpreted</strong> — a valid signature is not automatically trusted. Trust depends on the verifier policy.</li>
    <li><strong>Origin distinct from review</strong> — the source origin of an object is distinct from later human review or acceptance.</li>
    <li><strong>Unknown is not AI</strong> — missing provenance means unknown or unattested, not machine-authored by default.</li>
    <li><strong>Invalid is visible</strong> — stale, invalid, unsupported, or untrusted provenance SHOULD be made visible by provenance-aware tools.</li>
    <li><strong>Preserve when practical</strong> — tools SHOULD preserve provenance fields they do not understand when round-tripping source.</li>
  </ul>
</section>

<hr />

<section id="6-what-provenance-can-and-cannot-prove">
  <h2>6. What Provenance Can and Cannot Prove</h2>

  <p>A provenance attestation can provide strong evidence that an issuer signed a claim over a particular source state at a particular time. It can also show that the source object has or has not changed since that attestation, assuming the digest scope is well-defined and the verification algorithm is implemented correctly.</p>

  <p>A provenance attestation SHOULD NOT be described as an absolute proof that a human genuinely understood the code, that an AI was never involved, or that the resulting software is safe.</p>

  <table>
    <thead>
      <tr>
        <th>Provenance can support</th>
        <th>Provenance cannot guarantee by itself</th>
      </tr>
    </thead>
    <tbody>
      <tr>
        <td>A source object state was signed by a known issuer.</td>
        <td>The source object is correct or safe.</td>
      </tr>
      <tr>
        <td>A node or edge changed after an attestation.</td>
        <td>A human fully understood the object.</td>
      </tr>
      <tr>
        <td>An IDE classified an operation as direct human authoring, AI-assisted, imported, or reviewed.</td>
        <td>No automation was involved outside the observable authoring channel.</td>
      </tr>
      <tr>
        <td>A human review acceptance was recorded for a digest.</td>
        <td>The reviewer made no mistake.</td>
      </tr>
    </tbody>
  </table>

  <p>The credible FROG claim is therefore:</p>

  <pre><code>FROG can carry source-level provenance evidence and review state.
FROG does not magically guarantee safety merely because evidence exists.</code></pre>
</section>

<section id="7-provenance-object-model">
  <h2>7. Provenance Object Model</h2>

  <p>The recommended source shape is:</p>

  <pre><code>"ide": {
  "provenance": {
    "schema": "frog.source.provenance/0.1",
    "policy_hint": "non_executable_preserve",
    "attestations": [
      {
        "id": "att_01HX...",
        "subject": { },
        "claim": { },
        "issuer": { },
        "signature": { }
      }
    ]
  }
}</code></pre>

  <p>The object fields are:</p>

  <table>
    <thead>
      <tr>
        <th>Field</th>
        <th>Status</th>
        <th>Meaning</th>
      </tr>
    </thead>
    <tbody>
      <tr>
        <td><code>schema</code></td>
        <td>Recommended</td>
        <td>Identifier for the provenance object model version.</td>
      </tr>
      <tr>
        <td><code>policy_hint</code></td>
        <td>Optional</td>
        <td>Non-authoritative hint to tools. It MUST NOT replace local trust policy.</td>
      </tr>
      <tr>
        <td><code>attestations</code></td>
        <td>Recommended</td>
        <td>Array of authoring, generation, import, transformation, review, or acceptance claims.</td>
      </tr>
    </tbody>
  </table>
</section>

<section id="8-subject-model">
  <h2>8. Subject Model</h2>

  <p>An attestation subject identifies what source object, object group, or source state the claim covers.</p>

  <p>Recommended subject fields include:</p>

  <pre><code>"subject": {
  "kind": "diagram_node",
  "scope": "diagram",
  "id": "add_1",
  "digest": {
    "alg": "sha256",
    "value": "b64url..."
  },
  "digest_scope": "semantic_shape"
}</code></pre>

  <p>Allowed subject kinds SHOULD be extensible. The initial vocabulary includes:</p>

  <ul>
    <li><code>diagram_node</code></li>
    <li><code>diagram_edge</code></li>
    <li><code>diagram_region</code></li>
    <li><code>structure_node</code></li>
    <li><code>structure_region</code></li>
    <li><code>interface_port</code></li>
    <li><code>front_panel_widget</code></li>
    <li><code>widget_binding</code></li>
    <li><code>annotation</code></li>
    <li><code>local_state_object</code></li>
    <li><code>changeset</code></li>
    <li><code>document</code></li>
  </ul>

  <p>Tools MAY define namespaced subject kinds for implementation-specific authoring surfaces, provided they remain non-executable and safely ignorable by tools that do not understand them.</p>
</section>

<hr />

<section id="9-digest-model">
  <h2>9. Digest Model</h2>

  <p>A digest binds an attestation to a source state. The digest SHOULD be computed over a canonicalized representation of the covered subject, excluding the provenance attestation itself.</p>

  <p>The digest model SHOULD distinguish semantic shape from presentation shape when that distinction is useful:</p>

  <table>
    <thead>
      <tr>
        <th>Digest scope</th>
        <th>Meaning</th>
        <th>Example change</th>
      </tr>
    </thead>
    <tbody>
      <tr>
        <td><code>semantic_shape</code></td>
        <td>Source properties that affect validated meaning or source object identity.</td>
        <td>Changing a primitive from add to multiply.</td>
      </tr>
      <tr>
        <td><code>presentation_shape</code></td>
        <td>Layout and authoring-presentation properties.</td>
        <td>Moving a node on the canvas.</td>
      </tr>
      <tr>
        <td><code>full_source_shape</code></td>
        <td>The full covered source object shape under the chosen canonicalization rule.</td>
        <td>Any covered change.</td>
      </tr>
    </tbody>
  </table>

  <p>A tool MUST NOT treat a digest as proof of origin by itself. A digest only identifies content. Provenance evidence requires a claim and, when stronger evidence is needed, a signature or other authentication mechanism.</p>
</section>

<hr />

<section id="10-claim-model">
  <h2>10. Claim Model</h2>

  <p>The claim describes what is asserted about the subject.</p>

  <pre><code>"claim": {
  "activity": "create_node",
  "origin": "human_direct",
  "review_state": "not_reviewed",
  "tool": {
    "id": "com.graiphic.frog.ide",
    "version": "0.1.0"
  },
  "actor": {
    "kind": "user",
    "id_hash": "sha256:b64url..."
  },
  "time": "2026-04-25T10:42:13Z"
}</code></pre>

  <p>Recommended origin vocabulary:</p>

  <ul>
    <li><code>human_direct</code> — direct graphical authoring action by a human through a trusted authoring channel.</li>
    <li><code>human_guided</code> — human configured a guided tool that generated canonical source objects.</li>
    <li><code>ai_generated</code> — an AI system generated the source object or region.</li>
    <li><code>ai_assisted</code> — an AI system participated in the modification, suggestion, transformation, or completion flow.</li>
    <li><code>tool_generated</code> — deterministic or non-AI tooling generated the object.</li>
    <li><code>imported</code> — object came from an external artifact or package.</li>
    <li><code>snippet_inserted</code> — object came from a snippet or reusable authoring unit.</li>
    <li><code>unknown</code> — origin is not known or not attested.</li>
  </ul>

  <p>Recommended review activity vocabulary:</p>

  <ul>
    <li><code>review_accept</code></li>
    <li><code>review_reject</code></li>
    <li><code>review_request</code></li>
    <li><code>review_update</code></li>
  </ul>

  <p>The source origin of an object and the human review status of that object are separate claims. A source object may be <code>ai_generated</code> and later <code>review_accept</code> for the same digest.</p>
</section>

<hr />

<section id="11-signature-and-issuer-model">
  <h2>11. Signature and Issuer Model</h2>

  <p>A signature authenticates that an issuer made a claim over the attested subject state.</p>

  <pre><code>"issuer": {
  "id": "com.graiphic.frog.ide",
  "kind": "ide",
  "trust_domain": "graiphic"
},
"signature": {
  "alg": "Ed25519",
  "key_id": "graiphic-frog-ide-prod-2026-q2",
  "value": "b64url..."
}</code></pre>

  <p>The base source format MUST remain open to multiple issuers. The standard SHOULD NOT require that only one proprietary IDE can create conforming provenance. Instead:</p>

  <ul>
    <li>any tool MAY emit provenance attestations that conform to the source shape;</li>
    <li>each attestation declares its issuer;</li>
    <li>each IDE or organization decides which issuers are trusted under local policy;</li>
    <li>Graiphic IDE may recognize Graiphic-controlled issuers or certified third-party issuers without closing the source format.</li>
  </ul>

  <p>Signature algorithms SHOULD be declared explicitly. The base source format may permit multiple algorithms, but a stricter trusted-authoring profile MAY restrict accepted algorithms and issuer classes.</p>
</section>

<hr />

<section id="12-verification-states">
  <h2>12. Verification States</h2>

  <p>A provenance-aware verifier SHOULD classify each attestation into a visible state.</p>

  <table>
    <thead>
      <tr>
        <th>State</th>
        <th>Meaning</th>
      </tr>
    </thead>
    <tbody>
      <tr>
        <td><code>valid_trusted</code></td>
        <td>The digest matches, the signature verifies, and the issuer is trusted under local policy.</td>
      </tr>
      <tr>
        <td><code>valid_untrusted</code></td>
        <td>The digest and signature verify, but the issuer is not trusted under local policy.</td>
      </tr>
      <tr>
        <td><code>stale</code></td>
        <td>The source object no longer matches the attested digest.</td>
      </tr>
      <tr>
        <td><code>invalid</code></td>
        <td>The signature or attestation structure is invalid.</td>
      </tr>
      <tr>
        <td><code>unsupported</code></td>
        <td>The verifier does not support the algorithm, schema, subject kind, or canonicalization rule.</td>
      </tr>
      <tr>
        <td><code>missing</code></td>
        <td>No provenance is present for the object under the verification query.</td>
      </tr>
      <tr>
        <td><code>unknown</code></td>
        <td>The object has no reliable attestation or the verifier cannot establish a stronger state.</td>
      </tr>
    </tbody>
  </table>

  <p>Tools MUST NOT silently convert <code>missing</code> to <code>ai_generated</code>. Unknown source is not the same as machine-generated source.</p>
</section>

<hr />

<section id="13-trust-policy">
  <h2>13. Trust Policy</h2>

  <p>The source format defines how provenance can be carried. It does not force one universal trust policy.</p>

  <p>A trust policy may be owned by:</p>

  <ul>
    <li>an IDE implementation;</li>
    <li>a project;</li>
    <li>an organization;</li>
    <li>a certification workflow;</li>
    <li>a deployment profile;</li>
    <li>a future marketplace or issuer registry.</li>
  </ul>

  <p>Trust policy MAY determine:</p>

  <ul>
    <li>which issuers are trusted;</li>
    <li>which key IDs are accepted;</li>
    <li>which signature algorithms are allowed;</li>
    <li>whether AI-generated content requires human review before execution or deployment;</li>
    <li>whether stale or missing provenance blocks a workflow or only raises a warning.</li>
  </ul>

  <p>The base language MUST remain executable without a proprietary trust-policy engine. A stricter profile MAY impose additional gates for sensitive environments.</p>
</section>

<hr />

<section id="14-canonicalization-rules">
  <h2>14. Canonicalization Rules</h2>

  <p>Digest computation requires a deterministic representation of the covered source state.</p>

  <p>A provenance verifier SHOULD declare or infer:</p>

  <ul>
    <li>the subject selection rule;</li>
    <li>which fields are included;</li>
    <li>which fields are excluded;</li>
    <li>the JSON canonicalization procedure;</li>
    <li>the digest algorithm;</li>
    <li>the digest scope.</li>
  </ul>

  <p>The provenance object itself MUST be excluded from the digest of the attestation it carries. Otherwise the signature would recursively sign its own storage location.</p>

  <pre><code>source object
  -&gt; select covered fields
  -&gt; canonicalize
  -&gt; hash
  -&gt; sign attestation over digest and claim
  -&gt; store in ide.provenance</code></pre>
</section>

<hr />

<section id="15-preservation-and-degraded-reading">
  <h2>15. Preservation and Degraded Reading</h2>

  <p>Provenance is intended to survive normal source round-trips whenever practical.</p>

  <ul>
    <li>A tool that does not understand provenance SHOULD preserve <code>ide.provenance</code> when it preserves other unknown <code>ide</code> fields.</li>
    <li>A tool that modifies a covered source object SHOULD NOT leave a stale attestation visually presented as trusted.</li>
    <li>A tool that cannot verify an attestation SHOULD classify it as unsupported or unknown rather than trusted.</li>
    <li>A formatter SHOULD NOT delete provenance merely because it is non-executable.</li>
    <li>A runtime MAY ignore provenance for execution but SHOULD NOT rewrite source in a way that destroys provenance unless it is explicitly acting as a source transformation tool.</li>
  </ul>

  <p>Source provenance is not cache. It is not safe to delete merely because it can be recomputed by some tool. A signature made by an issuer over a specific source state is a source-carried audit artifact.</p>
</section>

<hr />

<section id="16-validation-rules">
  <h2>16. Validation Rules</h2>

  <p>The following source-level rules apply:</p>

  <ul>
    <li>If <code>ide.provenance</code> exists, it MUST be a JSON object.</li>
    <li>If <code>attestations</code> exists, it MUST be an array.</li>
    <li>Each attestation SHOULD have a stable <code>id</code>.</li>
    <li>Each attestation SHOULD identify a <code>subject</code> and a <code>claim</code>.</li>
    <li>Signed attestations SHOULD identify an <code>issuer</code> and <code>signature</code>.</li>
    <li>Source structural validation MAY reject malformed provenance objects if the claimed schema version is known and violated.</li>
    <li>Source structural validation MUST NOT treat missing provenance as invalid base FROG source.</li>
    <li>Semantic validation MUST NOT depend on provenance to determine what the program computes.</li>
  </ul>
</section>

<section id="19-security-considerations">
  <h2>19. Security Considerations</h2>

  <p>Source provenance improves inspectability and accountability, but it introduces new security responsibilities.</p>

  <ul>
    <li>Private signing keys MUST be protected by the issuer.</li>
    <li>A compromised IDE or compromised signing key can emit misleading attestations.</li>
    <li>Verification UI MUST distinguish valid, trusted, untrusted, unsupported, stale, invalid, and missing states.</li>
    <li>Human review signatures SHOULD be tied to an explicit digest so that later edits invalidate or supersede the review.</li>
    <li>Actor identifiers SHOULD be privacy-aware. A project may use pseudonymous or hashed actor references instead of exposing personal identifiers in source.</li>
    <li>Provenance SHOULD NOT be used as a substitute for semantic validation, conformance, testing, code review, safety analysis, or deployment authorization.</li>
  </ul>
</section>

<section id="20-summary">
  <h2>20. Summary</h2>

  <p>Source provenance gives FROG a source-carried way to make human, AI, tool-generated, imported, reviewed, unknown, stale, invalid, unsupported, and untrusted authoring states visible to tools and reviewers.</p>

  <p>The standardized home is <code>ide.provenance</code>. The object is optional, non-executable, source-carried, and safely ignorable by runtimes and compilers for execution semantics.</p>

  <pre><code>Source provenance should make authorship evidence visible.
Source provenance should not become executable truth.
Missing provenance means unknown, not AI-generated.
Human review acceptance is distinct from original origin.</code></pre>
</section>
