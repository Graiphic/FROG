# Visual programming and human control

**Project philosophy · reviewed 11 November 2026 · Non-normative**

Graiphic develops a graphical programming environment in which engineers can build software, understand how it works and change it with control over the result. FROG is the open dataflow language foundation; Graiphic Studio is Graiphic's proprietary environment for putting that foundation to work.

The project serves everyday programming and the lifetime of an application: interface design, composition of behavior, execution, debugging, maintenance and supported deployment. Human-authored software, a colleague's program and a proposal generated by an AI tool all need to remain understandable and editable. AI increases the relevance of that need; the project also has value whenever people develop and maintain software themselves.

## A visual representation people can work with

Connections expose dependencies. Structures organize cases, repetition and state. Labels, shapes, color and spatial organization help people navigate the program and find the detail relevant to a question. These visual resources are part of the programming experience, rather than a picture produced only after development.

A useful overview preserves access to the underlying behavior. Engineers need to move from architecture to an individual case, terminal or value without losing their place. Layout helps navigation; the language's actual connections, structures and effects determine meaning. A dense graph or a hidden effect can still be difficult to understand, so readable hierarchy and practical editing remain design work.

## Connect understanding to execution and correction

Studio brings interface design, the Block Diagram and Source into one workflow. For supported programs, Run and Highlight connect the represented logic to an execution. Values and activity can be examined in context, and an engineer can return to the relevant logic to make a change.

The intended benefit is practical: understand an unfamiliar program, locate an unexpected result, make a valid correction and check the version that runs. Stable associations between the document, its types, the execution and its observations help preserve that continuity. They support development and maintenance even when no formal-verification tool is involved.

## An open language and an integrated product

FROG's public source, type, semantic and FIR contracts provide a foundation for independent implementations and tooling. Studio develops the integrated experience: authoring, navigation, diagnostics, execution observation and Build. The language, editor, compiler and target have distinct responsibilities.

Supported tools and human authors should be able to work from compatible representations of the program. Future source-language imports must preserve the relevant behavior and context within their declared scope. General imports from C, C++, Rust, JavaScript or Java remain prospective; machine-readable source does not by itself establish those bridges.

Openness, official project leadership and product ownership retain their existing [governance](../GOVERNANCE.md#official-project-rules), [contribution rules](../CONTRIBUTING.md#contribution-rules) and licenses. FROG remains open; Studio remains proprietary. Shared components follow the established path of qualification and explicit integration.

## Keep program meaning distinct from deployment choices

The separation between language meaning and target-specific execution enables different consumers and future compiler or hardware bridges. Every implemented bridge still needs its own supported profile, dependencies and evidence. A diagram that can be edited is not automatically executable on every target.

The existing foundation includes the public common Frontend and selected normal Run, Highlight and LLVM/native paths on Windows/x86-64. The [9 November checkpoint](../docs/frontend-checkpoint-2026-11-09.json), [project status](../FROG-Project-Status.md) and individual dossiers retain their own scope. Additional deployment targets remain future work.

Continue stabilizing source/profile documentation and the supported execution path. After stabilization, language-import development and missing-function/performance work can progress within the maintained roadmap; additional compiler bridges follow their own readiness decisions. This philosophy states the direction without starting a separate implementation campaign.

## Evaluate ideas by their value to the project

Useful ideas from a presentation, customer discussion or research contact can improve the common product. Assess whether an idea addresses a broad user need, fits the architecture and can be maintained at a reasonable cost. A partner's interest alone does not make it a core requirement.

Partner-specific demonstrators, formal-verification adapters and specialized embedded guarantees can be worthwhile extensions or collaborations. Their scope, resources and success criteria stay separate from the general product roadmap. Common improvements should enter the core only after their wider value and integration cost have been assessed.
